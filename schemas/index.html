Schemas

The data the engine runs on

How a client's intake becomes comparable to a job posting, and how an application's status gets tracked over time. These are working schemas for the engine — not client-facing documents — kept here so the qualification gate compares real structured values instead of guessing at text.

DESIGN-NOTES.md

Reference — design rationale

Why the four schemas below are shaped the way they are, the conventions they follow (JSON Resume, JSON Schema 2020-12), and the open questions still being resolved with the qualification-gate and resume-tailoring work.

Read the notes →

shared-defs.schema.json

Complete

The shared vocabulary — skills, remote policy, salary, seniority — that the client and job-posting schemas both reference, so a client's profile and a job's requirements can be compared directly instead of fuzzy-matched.

View the schema →

client-profile.schema.json

Complete

The structured form of a client's intake — skills, work history, qualification bar, exclusions, screening answers — derived from their resume and intake form. One file per client.

View the schema →

job-posting.schema.json

Complete

A normalized snapshot of one scraped job posting, shaped to compare directly against a client profile. Immutable at scrape time.

View the schema →

application-tracking.schema.json

Complete

The per-application tracking record — qualification result, status history, resume version used — one file per client/job pair. This is what the client feed's status indicator reads from.

View the schema →

skills-taxonomy.json

Living — starter set

The controlled vocabulary of skill IDs both schemas reference. A 34-skill starter set spanning common white-collar categories; grows as real clients and postings come in.
